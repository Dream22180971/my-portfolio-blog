# 资讯聚合、筛选与文章发布工作流

这套流程的目标不是“读完所有资讯”，而是让每条高价值信息经过证据核验、形成独立判断，并最终成为可审核、可发布、可复盘的文章资产。

## 一、职责边界

| 角色 | 主要职责 |
|---|---|
| Inoreader | 聚合资讯、主题分流、保留候选素材 |
| Codex | 筛选候选、核验来源、形成选题、写初稿、接入博客并自测 |
| GitHub | 管理选题状态、保存文章差异、运行 CI、承载审核记录 |
| 邮箱 | 发送需要处理的提醒和周期摘要，不作为正文或审核记录的唯一来源 |
| Sean | 审核观点、补充个人经验、决定是否发布 |

## 二、端到端状态流

```text
Inoreader 新资讯
  → 稍后读
  → Frame / Verify / Build / 待写选题
  → GitHub 选题 Issue
  → 独立写作分支
  → 本地文章初稿
  → lint / build / verify:site / 浏览器验证
  → Draft PR
  → 邮件提醒审核
  → 审核通过
  → 合并 main
  → Vercel 发布与线上验证
  → Issue 复盘并关闭
```

## 三、每个阶段的完成标准

### 1. 聚合

- 来源进入正确的 Inoreader 文件夹；
- 不追求清空未读；
- 每天最多保存 3 条候选；
- 纯营销稿、无来源转载和重复新闻直接跳过。

### 2. 筛选

候选至少满足两项：

- 有真实案例、数据或失败经验；
- 能支持一个明确判断；
- 与软件测试、AI 测试、质量工程或 AI 产品化直接相关；
- 可以转成方法、清单、对比或复盘；
- 来源可访问，关键事实可交叉核验。

每个候选要留下四项最小信息：

| 字段 | 内容 |
|---|---|
| Frame | 真正要回答的问题 |
| Verify | 哪些事实已证实，哪些仍是推论 |
| Build | 对读者可落地的方法或步骤 |
| 写作判断 | 为什么值得写，以及与已有文章的差异 |

### 3. 立项

在 GitHub 创建 `content-candidate` Issue，内容包括：

- 暂定标题；
- 原始来源和发布日期；
- 目标读者；
- 一句话核心判断；
- Frame / Verify / Build；
- 已核验事实；
- 待补充的个人经验；
- 与站内旧文章的差异；
- 预期文章类型和完成标准。

推荐状态标签：

```text
content-candidate → researching → drafting → review → approved → published
```

### 4. 写作

- 每篇文章使用独立分支；
- 先写核心判断，再安排结构；
- 区分来源事实、作者推论和待验证信息；
- 外部案例不能冒充自己的实践；
- 至少提供一个可复用框架、检查表或实施步骤；
- 标题、摘要和正文必须回答同一个问题。

### 5. 自测

提交审核前必须完成：

```text
npm run lint
npm run build
npm run verify:site
git diff --check
```

并在本地浏览器检查：

- 文章列表能看到新文章；
- 文章路由返回 200；
- 标题、摘要、章节、表格和链接正常；
- 返回文章列表等基础交互正常；
- 浏览器控制台没有错误。

### 6. 审核

Draft PR 是唯一审核入口，重点检查：

- 观点是否符合个人立场；
- 是否需要补充自己的项目案例；
- 来源和数字是否准确；
- 是否存在夸大结论；
- 是否与旧文章重复；
- 是否允许进入发布阶段。

审核结论只保留三种：

```text
Approve：允许发布
Request changes：按评论修改后复审
Close：本次不发布，保留选题原因
```

### 7. 发布

只有审核通过后才允许：

1. 合并到 `main`；
2. 等待 GitHub CI 与 Vercel 部署；
3. 检查生产文章 URL、canonical、sitemap 和页面内容；
4. 将选题 Issue 标记为 `published`；
5. 记录发布时间、生产 URL 和后续数据观察点。

## 四、GitHub 如何提升效率

### 方案 A：立即可用，不增加自动化

- 一个选题对应一个 Issue；
- 一篇文章对应一个分支和一个 Draft PR；
- 当前 CI 自动执行 `npm run check`；
- 审核意见全部写在 PR，不散落在聊天或邮件正文；
- Issue 负责“为什么写”，PR 负责“具体写成什么”。

这是最小但完整的版本，维护成本最低。

### 方案 B：审核通过后再实施

增加两个模板：

1. `.github/ISSUE_TEMPLATE/content-candidate.yml`
   - 强制填写来源、核心判断、Frame / Verify / Build 和待核验事项。
2. `.github/pull_request_template.md`
   - 强制勾选来源核验、重复检查、lint、build、站点验证和本地浏览器检查。

模板不会替代判断，但能防止遗漏关键步骤。

### 方案 C：稳定运行后再自动化

增加一个每周定时 GitHub Action：

- 汇总仍处于 `content-candidate`、`researching`、`review` 的 Issue；
- 创建或更新“本周内容工作台”Issue；
- @mention 审核人；
- 依赖 GitHub 自带通知发送邮件，不额外保存 SMTP 密钥。

GitHub Actions 的定时任务运行在默认分支，可使用 POSIX cron；正式启用前需要先确认执行频率、权限和仓库通知设置。

## 五、邮箱如何提升效率

邮箱只承担“提醒我该处理什么”，不承担“保存全部内容”。

推荐建立三个过滤标签：

| 邮箱标签 | 进入条件 | 处理动作 |
|---|---|---|
| `资讯/Newsletter` | 订阅邮件和行业周报 | 需要写作的内容转入 Inoreader 或选题 Issue |
| `GitHub/待审核` | Review requested、PR 评论、CI 失败 | 当天处理 |
| `GitHub/已完成` | PR 合并、部署成功 | 自动归档，周复盘时查看 |

通知策略：

- Issue 被指派、PR 请求审核和 CI 失败：立即邮件；
- 普通仓库动态：仅 Web 通知或每日摘要；
- Push 邮件：默认不启用，避免每次提交都打扰；
- 每周内容摘要：由 GitHub Issue 汇总后触发邮件，而不是单独维护邮件模板。

## 七、运行节奏

### 每天 15 分钟

1. 浏览四个主题文件夹；
2. 最多保留 3 条；
3. 对最强的一条补齐四个写作标签。

### 每周一次

1. 从 `待写选题` 选出一个核心选题；
2. 建 Issue；
3. 完成一篇可审核初稿；
4. 清理长期无进展候选。

### 每月一次

1. 淘汰低价值 RSS 源；
2. 统计候选到文章的转化率；
3. 统计审核修改最多的问题；
4. 更新模板和筛选标准。

建议先连续运行四周，再决定是否增加 GitHub Action、邮件自动转发或大模型 API 自动摘要。
